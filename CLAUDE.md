# Phenox (NASA Space Apps)

Will a material burn in a given spacecraft atmosphere? Answered from real NASA PSI combustion tests.

## Layout

- `scrape_psi.py`, `load_to_tigerdata.py`, `schema.sql` — data pipeline into Tiger Data (Postgres). See README.md.
- `worker/fireline-verdict/` — Cloudflare Worker. `POST /verdict` with `{ o2_fraction, pressure_atm, material }` returns facts only (nearest tested bucket, relation, evidence, fallback). It never decides PASS/CAUTION/FAIL. `GET /health` for a DB check. `GET /points` returns every test with oxygen on record, as arrays in `columns` order; its last column, `extra` (added 15 Nov 2026), carries the conditions set before a test for tests with a clear ending, copied from the original row for the page's model estimate. It must never include anything measured during or after a test.
- `web/index.html` — the front end. One static file, no build step, no required dependencies (Motion and three.js are optional CDN imports, see Design). Deployed as Cloudflare Static Assets from the worker's `wrangler.jsonc` (`assets.directory` points at `web/`), so `wrangler deploy` / `wrangler dev` in the worker folder serves the UI at `/` and the API on the same origin. API URL defaults to the page's origin when the worker serves it, otherwise to the deployed worker `https://fireline-verdict.fireline-team.workers.dev`; override with `?api=` or the Settings field. `?mock=1` (or the Settings checkbox) runs on synthetic data with a visible banner.
  - Scenario picker: ISS / Lunar / Mars / Spacesuit / Custom presets (psia in the UI, atm to the worker), a candidate-material list, and a pressure sweep from nominal down to a depress floor (4 points). Since 15 Nov 2026 the panel (`.panel.atmo`) shows the presets as cards, oxygen and the two pressures as readout cards with a unit inside the input and a level bar (oxygen of 100%, pressure of 20 psia, set in `updateConv()`), the sweep's four pressures as chips (`#sweepLine`, same formula as the ranking), the preset note as a callout, and the materials under a Step 2 label. Each material × point is one `POST /verdict`; requests run 4 at a time.
  - The reading and recommendation are computed in the page from the worker's facts (see "How the readings are made" on the page and the `assess()` function). Keep that rule and the on-page explanation in sync. Changed 15 Nov 2026: the words are Goes out / Mixed / Keeps burning / No data, not Pass / Caution / Fail, because every test was ignited on purpose and the data says how the flame ended, not whether a material is safe. Only "went out" and "kept burning" outcomes are conclusive; droplet disruptions and unrecorded results are left out; a nearest bucket more than 2 bucket widths away is No data; the share is shown with a 95% Wilson interval instead of a confidence score. The CSS classes are still `ok` / `warn` / `bad` / `none`. The worker's chat prompt uses the same words and is told never to say PASS/CAUTION/FAIL or call a material safe.
  - Model estimate (added 15 Nov 2026, rebuilt the same day on the tests' own conditions): under each ranking card's reading, a `Model`-tagged line from a logistic regression trained in the page (`modelRows()`, `trainModel()`, `modelFor()`, `modelLine()` beside `assess()`). It learns from tests that went out or kept burning, using only conditions set before each test, which the worker's `/points` sends in the `extra` column (original NASA headers and text, read loosely by `xval()` / `xnum()`). Two kinds of test, each with its own fit: droplets (FLEX, PSI-69: fuel, oxygen, pressure, the carbon dioxide and helium in the atmosphere, starting droplet size; each fuel has its own oxygen and size slopes) and gas jets (CFI-G normal flames, PSI-159: fuel, oxygen, pressure from the "approx p (bar)" column the loader missed, fuel flow rate, fuel dilution). Left out on purpose: inverse flames (their oxygen figure is the injected gas, not the atmosphere, and training on them made the normal-flame estimates worse), community uploads, and anything measured during or after a test (burn time, extinction diameter, peak temperatures), which would leak the answer. Fuels need at least `MODEL_MIN` = 15 usable tests. Newton's method with a ridge penalty (`RIDGE` = 0.1), 200 bootstrap refits with a fixed seed for the 95% range, 5-fold cross-validation repeated 5 times and reported in `#modelNote`. An estimate is for an oxygen and nitrogen atmosphere, averaged over the droplet sizes (or flow rates and dilutions) NASA tested for that fuel; droplet lines also give the 2 mm and 4 mm figures. Every estimate says how many of the fuel's tests are near the scenario (within 5 points of oxygen and a factor of 1.5 in pressure), flags it under 5, and gives none at 0, outside the fuel's tested oxygen or pressure, or for a fuel it did not learn. It says "would go out on their own", never safe, never shows a flat 0% or 100%, and never changes the reading or the ranking order. No libraries, no build step. As of 15 Nov 2026: 345 tests of 5 fuels (heptane, methanol, butane, ethane, propane); 87% of held-out endings right against 83% for always guessing "went out", and 47% of the kept-burning flames caught. With only fuel, oxygen and pressure it could not beat the guess (76% against 76%), so do not drop the `extra` inputs, and do not quote an accuracy the page does not compute. If a live `/points` response has no `extra` (an older worker or a cached response), the page takes it from `web/points.json`, matched by test id and only where the rest of the row agrees.
  - The page also loads the test table once (`GET /points`, then `web/points.json`, the same order as `viz.html`). It uses it to count outcomes in the nearest bucket (only when its row count matches the worker's `n_tests`, otherwise it counts the worker's evidence rows and says so), to draw "Where NASA tested each fuel" (an oxygen × pressure table per ranked fuel with the mission outlined), for the fuel picker under the materials box, for the CSV export, and for the investigation list.
  - Test-result colours (`--r-out`, `--r-disrupt`, `--r-burn`, `--r-unknown`) are the 3D page's: results, not readings, always in that order.
  - Investigation list ("Investigations for this atmosphere"): all investigations from the test table, ordered by whether their tested oxygen range covers the form's oxygen, then by gap, then fire-safety area before general science, then test count. Area and hardware tags are read from the title. It also tries `GET /investigations` (`[{ accession, title, doi, objective, n_tests }]`) for objectives; the worker does not have that route yet, so no objective text shows.
  - Mission Control box calls `POST /chat` with `{ message, model }` and shows `reply`. `model` is `grok` (xAI `grok-4.20-non-reasoning`, the default, key in the `XAI_API_KEY` secret) or `gemini` (through Cloudflare AI Gateway); the picker in the panel sets it and the AI briefing uses the same choice. The model first sorts a question into a lookup (a material in an atmosphere, answered from `buildVerdict()`) or general (counts, lists, how the data works, answered from an overview query of the whole table: totals, top 30 fuel names, investigations, outcome counts). The page prefixes the message with the form's oxygen and pressure so questions need not restate them.
  - Mission environment (top of the navy section, `#env-h`): a schematic of where the chosen preset is (Earth and the ISS, the Moon, Mars), a close/wide toggle, a live 3D view of the same place (NASA's Eyes on the Solar System in an `<iframe>` with `?embed=true`, created only when the stage scrolls into view and skipped when offline; an outside runtime dependency, like the optional CDN libraries), a link that opens it in a new tab, and an optional link to a locally running OpenSpace desktop app (WebSocket `ws://localhost:4682/websocket`, Lua camera commands). Since 15 Nov 2026 the 3D view spans the full width at up to 72% of the screen height, and the side panel (mission specifications, material readings, supporting evidence) sits under it in three columns, one column on narrow screens. That panel mirrors the form's oxygen and pressure and the latest ranking. Since 15 Nov 2026 (branch `Claude-openware-tool-change`) the panel follows the view: place buttons (Earth orbit, Moon, Mars) pick the matching mission preset in the form on the user's click, the same as clicking that preset card, so the atmosphere, panel and 3D view change together (pressing the place already shown resets NASA's viewer to it); Mission specifications adds what the camera shows for that place and close/wide view, the gravity there, and which 3D source is live; after a place or atmosphere change, Material readings offers a "Rank materials for this place" button that presses Rank materials. When OpenSpace is connected (still only after Connect), the block subscribes to its camera anchor (`NavigationHandler.OrbitalNavigator.Anchor`, falling back to asking every 2 s with a Lua `return`) and switches the page to Earth orbit, the Moon or Mars when the user flies there in OpenSpace, without flying OpenSpace again; any other anchor gets a note that it is not a Phenox mission place. Where the user flies inside NASA's Eyes cannot be read (a cross-origin iframe with no API), and the caption says so. It is display only: it computes no verdicts and receives them through the `fireline:ranked` event that `render()` dispatches. The Mars preset's figures (34% oxygen, 8.2 psia, 7 psia floor) and the lunar and Mars camera sites are placeholders to confirm.

  - Flame lab (`.lab.f-lab`, heading `#lab-h`): a compact white card in the hero, right of the headline (one column under 1100px), so the hero ribbon runs through its chamber. Cut down on 15 Nov 2026 to five controls: mission (ISS, Moon base, Mars habitat, Spacesuit: each sets oxygen, pressure and gravity; Moon and Mars gravity leave both gravity buttons unchecked), gravity (Microgravity / Normal gravity), fuel (heptane, methanol, dodecane, PMMA; each matched to NASA fuel names by a regex in `FUELS`), oxygen and pressure. The modes, the other missions, cabin air, airflow and gravity sliders, and telemetry were removed; do not bring them back without asking. Its own script (between the app and decoration scripts) publishes `window.phenoxLab` and a `phenox:lab` event; the decoration script's flame shader and the hero ribbon only read them (`flow`, `heat` and `haze` stay 0). It is an illustration from rough combustion rules of thumb (per-fuel oxygen limits, thin air below 5 psia, still-air starvation in microgravity; `limitFor()`), labelled as not a reading, and uses its own words (Burning / Barely burning / Flame out), never the ranking's. It follows the form's oxygen and pressure when those change. The burn-rate meter under the chamber window (`.burn-meter`) is driven by the NASA tests: the app shares its loaded test table read only (`window.phenoxPoints` and a `phenox:points` event), and for the lab's fuel, oxygen and pressure the lab takes the nearest tested conditions (bucket widths of 5 points of oxygen and 0.1 atm, nothing past 2 widths, as in the ranking) plus everything within one width; their average burn rate against that fuel's fastest on record fills the meter, and it flickers when the share of conclusive tests that kept burning is below a third. A line under the controls shows those counts. The "Check this in the NASA data" button copies the lab's oxygen, pressure and fuel into the ranking form on click, as if typed, and focuses Rank materials; it does not run the ranking.

- `web/methods.html` — "How it works", linked from the first item of the main nav (it replaced the Atmosphere anchor on 15 Nov 2026; the Rank materials pill still goes to the form). One static file, no libraries. Eight numbered steps from NASA's files to the reading: outcome classes, `width_bucket` buckets, the nearest-bucket distance, the conclusive share, the thirds thresholds and the two downgrade rules, the Wilson interval (with a slider demo against the textbook range), and the pressure sweep. Formulas are plain HTML. Counts and the heptane-in-ISS-air worked example are computed from `/points`, then `points.json`. It restates `assess()`, so change it in the same edit whenever that rule changes.
- `web/viz.html` — the 2D plot of the data, opened by the hero's "Visualize the data" button (same tab). One static file, no 3D library. It plots every test that recorded an oxygen level against oxygen, with a switch between burn rate (the tests with a comparable burn rate) and the chance it goes out, plus trend lines (least-squares fits per fuel and overall, or a moving share with a Wilson 95% band) computed from the tests currently shown. A scenario bar (oxygen, pressure, fuel, mission presets, side by side) gives a verdict card from the nearest tests. Data order: the worker's `GET /points` (live), then `web/points.json` (a real-data snapshot of the same query), then a labeled mock set (`?mock=1`). The five charts (funnel, outcome share by oxygen band, burn rate scatter, oxygen histogram, top investigations) sit below the plot on the same page; clicking a bar lights those tests in the plot. The earlier 3D model was removed.
- `web/research.html` — the research behind the readings: NASA FLEX and other published papers (Nayagam et al. 2013 on NTRS, Olson & Ruff 2009, Friedman 1999, Saffire, SoFIE and more), each linked by DOI or NTRS id, plus a live check that our methanol rows agree with the published 12–13% oxygen limit. Summaries are paraphrases of the abstracts; do not add a claim you have not read in the source. Linked from the nav, methods.html and the viz rail.
  - Every number in its "Key findings" is computed in the page from the loaded rows. Never hardcode a statistic there.
  - Result colors (blue went out, orange kept burning, green droplet broke apart, grey not recorded) are test results, not verdicts, so they deliberately do not reuse the pass/caution/fail colors. Each also has its own shape.
  - If the data is reloaded, regenerate `web/points.json` from the `/points` response. Save the response as it is: the main page's model estimate needs its `extra` column.

- `web/flammability.html` — the 3D flammability map of one fuel, opened in a new tab from the "See this fuel's flammability map in 3D" link on a quantified ranking card (`?material=&o2=&p=`, oxygen in percent, pressure in atm). One static file, plain WebGL, no libraries. Left to right is oxygen, front to back is pressure, and each block is one tested bucket (the worker's own: 5 points of oxygen by 0.1 atm, up to 2 atm). Block height is the share of that bucket's tests that kept burning, or the average burn rate; block colour is pass, caution or fail by the ranking's thresholds. Pins mark the mission presets and the scenario handed over. Same data order as `viz.html` (`GET /points`, then `web/points.json`, then a labeled mock).
  - It uses the ranking's burn rule on purpose (only outcomes containing "extinct" or "disrupt" count as not burning), so a block and a verdict never disagree. If `assess()` or the envelope view changes, change `buildFuel()` and the page's "How to read this" text with it.
  - The table under the model is the keyboard route and the no-WebGL fallback; keep every number in the model present there.

## Rules for the front end

- Keep it a single `web/index.html` unless there is a strong reason not to. Touch as few files as possible.
- The reading (Goes out / Mixed / Keeps burning / No data) is a documented heuristic in the page, not NASA guidance. Always show the evidence behind it (bucket counts, relation, investigation id, DOI) next to the badge, and never present it as a certification.
- Send `o2_fraction` as a 0–1 fraction (the form takes a percent and divides by 100). The worker rejects values over 1.

### Design

- Direction: white and NASA red (chosen 14 Nov 2026). A small red "Project" line above a huge navy "Phenox" title (no period since 15 Nov 2026) on a white-grey top section with the flame chamber beside it, then a deep navy section holding results, investigations and chat as navy cards. Pill-shaped buttons and presets.
- Tokens live in `:root` in `web/index.html`; use them, do not hardcode new colors.
- Feature panels (15 Nov 2026): each feature is a `.feature` panel with an `f-*` class and a `data-feature` name tag. They keep the page's own colours and alternate shades so neighbours read apart: on navy, Material ranking, the pressure sweep, Investigations and Contribute data are the lighter panel (white 7% over `--char`), Test map, How it works and Mission environment the darker one (black 28% over `--char`). In the light section the Flame lab card and the Mission atmosphere panel stay white on the grey page. No per-feature hues.
  - Light section: grey `#eef1f5`, paper `#ffffff`, navy ink `#0b1b33`, secondary ink `#47556b`. Navy section: `#0b1f3f`, cards `#132b52` / `#1b3766`, text `#f2f5fa`, secondary `#b6c3d8`.
  - Accent red `#d42a1c` with white text is for actions in the light section only (Rank materials, How it works, the orbit line). In the navy section red means Fail and nothing else: buttons there are white, links and focus rings are sky blue `#9cc4ff`.
  - Verdicts on navy: pass teal `#45d2c3`, caution amber `#f6b445`, fail coral `#ff8a7a`, no data `#a9b4c6`.
- Icons are Tabler Icons (MIT) fetched once from Iconify and inlined as CSS variables (`--i-*`), so there is no runtime dependency. Presets, section headings and Settings use them as masks; result cards show a round badge (droplet for liquid fuels, stack for solids) chosen by the decoration script from the material name.
- Verdicts are always word + shape icon + evidence line: tick in a circle (pass), ! in a triangle (caution), cross in an octagon (fail), dash in a square (no data). Never color alone.
- Type: Space Grotesk from Google Fonts, one family, weights 300 to 700. Sentence case everywhere.
- The flame is a TSL shader (three.js) on a canvas filling the porthole (blue ringed sphere in cabin air, orange fireball in rich oxygen). It reads the oxygen field and pauses off screen. If three.js or WebGL is missing, the CSS `#flame` gradient shows instead. No 3D models or images.
- The page has two scripts. The first is the app (settings, worker calls, verdict logic, rendering). The second is decoration only (flame shader, particle loader, burn transition, count-up numbers, pointer spotlight on cards, table roles): it reads what the app rendered and must never fetch data or change app state. A third script is the Mission environment block; it also never fetches or changes app state, and it must never open the OpenSpace socket on its own. Chrome shows a local-network permission prompt when a public page reaches for localhost, so the socket opens only when the user presses Connect, with no automatic retries.
- Libraries: the decoration script dynamically `import()`s, from jsDelivr at pinned versions, Motion (`motion@14.14.0`, plus `motion@14.14.0/three` for `threeEffect`) and three.js (`three@0.187.0/build/three.webgpu.min.js`; TSL is `THREE.TSL` from the same module, so no import map). `WebGPURenderer` falls back to WebGL2 on its own. All of it is optional: if any import fails, the CSS keyframes, the `--spring` curve, the CSS porthole and flame, and the CSS loader ball do the job, so never make the page depend on them.
- Chamber: the flame lab shows a flat SVG combustion test chamber (`.orb.rig`, `.rig-art`, viewBox `30 22 140 244`), like the sealed vessels NASA burns fuels in on the ISS. It replaced a rocket engine on 15 Nov 2026 because the challenge puts rockets and propellants outside the PSI data's scope; do not bring back nozzles, plumes or exhaust. Kept simple on purpose (same day): a plain pressure vessel with a domed lid and dished base bolted to a steel cylinder, a viewing window, a stencil, and the NASA burn-rate meter slot under the window (`.burn-meter`, coloured by `--meter-c`); no bottles, gauges, valves or vents. Its square window is the `.chamber` (the flame shader fills it). The CSS positions of `.chamber` and `.burn-meter` are the window and slot as shares of the viewBox, so change them together. Soft SVG drop shadow. All vector, no images. The older porthole notes below describe the CSS that is still in the file but no longer in the markup. Previously: flat, not 3D (chosen 14 Nov 2026; the three.js satellite with solar panels was tried and removed). A brushed-steel ring (`.housing`: conic-gradient steel, ribbed rim) with SVG grooves and eight bolts around a glass porthole (`.chamber`) that holds the flame. The sun is upper left: a fixed highlight, a glass reflection, a streak that crosses the metal every few seconds (`.glint`) and two star glints (`.flare`), all CSS. No dishes or solar panels. Colors are the `--steel-*`, `--glare` and `--glass*` tokens.
- Motion: a particle-fire loader adapted from motion.dev's three/TSL particle example. One overlay (`#boot`, reused for every ranking) shows instanced dots that are born in a white-hot core and stream out along noise tongues, heating from blue to white-hot with progress, above a large percent and one thin progress line. When the work is done, the live page is drawn into an SVG `foreignObject`, read back one pixel per dot, and the dots spring (Motion `threeEffect` on the `globe` uniform) into that picture, so the dots build the page before the overlay fades. During a ranking the result cards stay hidden (`#ranking.dealing`, visibility only, so they keep their slots) until the loader has fully gone; then they rise in one after another and the numbers count up. A CSS ball (`.blaze:not(.gl)`) stands in until the particles load. Switching mission mode burns the changed text (`#presetNote`, the `.conv` lines, `#flameNote`): a fire front sweeps from the left edge of the screen, glyphs glow orange and crumble into ash dots, and the new text rebuilds behind it. Also: flame reacting to oxygen; results appearing or re-ranking as one View Transition; a height tween on the investigation list when filtering; numbers counting up when results arrive; a spotlight following the pointer on cards. Everything else under 0.5s, and all of it off or static under `prefers-reduced-motion` (no loader, no burn, flame and glare still). One entrance sequence on page load is allowed: the particles burn as a circle of fire while loading, then pull into a ball and fly on a spring into the chamber's porthole, cooling to the chamber flame's colour, while the dark backdrop fades (`.blaze.landing`) and everything slides into place (top bar drops, wordmark slides in from the left, hero text and facts rise, chamber settles). The particle canvas is transparent over the CSS backdrop for this. Rankings keep the ball and the dots-build-the-page ending. If the particles never ran, the same slide-in plays when the CSS ball leaves. Rest state visible if it never runs. No per-section fades, no scroll effects, no parallax.
- Hero background: a ribbon of fire-dust, after the stippled particle-wave look (a TSL shader on `canvas.wave-gl`, first child of `body`, behind everything, pointer-events none). One flowing, twisting sheet made of fine one-pixel grain runs across the hero through the Flame lab's chamber window (the lab card sits in the hero, so the ribbon and the fire it reacts to are in one section): dense where it faces you, a bright rim where it curls, thin at the twists, the grain drifting along it, with a light dust near the chamber. It swells, twists faster and thickens with oxygen, takes the flame colour near the chamber (blue in cabin air, orange in rich oxygen) and gold (`--caution`) further out, flickers with the flame. It does not react to the pointer (the cursor lens was removed on 15 Nov 2026). Since 15 Nov 2026 it follows the chamber's fire through `window.phenoxLab` (read only, the same state the porthole shader eases toward): heat rings breathe out of the chamber window and push and light the grain (stronger with oxygen, none when the flame is out), the flicker keeps the flame's turbulence pace, airflow carries the hot part downstream, gravity lifts it, and a flame-out cools the dust by the chamber to ash grey (`--ink-2`). Its colour and heat use the lab's oxygen when the lab exists, otherwise the form's. Not thin lines, not a regular dot grid. Opacity capped at .55 so hero text stays readable, faded out over the facts strip, swell scaled down on narrow screens. Pauses off screen, one still frame under reduced motion; without WebGL there is no background.
- The hero facts strip (2,954 tests, 26 investigations, 361 with oxygen and pressure) is static text taken from the worker's `/health` and the README on 14 Nov 2026. Update it by hand if the data is reloaded.
- Wordmark fire: the fire is inside the letters of "Phenox", never over or around them. A TSL shader canvas (`canvas.title-fire`, inside `.title`, which is `fit-content` and `position: relative`) is masked by the glyphs: the text is drawn into a 2D mask with the page's own font, letter spacing and baseline, and only those pixels show. Each letter is navy at the top with tongues rising from the baseline: red edges (`--accent`), orange body (`--blaze-warm`), amber only in the hottest pockets (`--caution`), sparks in `--blaze-hot`. Since 15 Nov 2026 the fire shows at half strength (`DIM = .5` in the shader, blending toward the navy), so the letters read navy first. The HTML text stays for layout and turns transparent (`.title.gl`) only once the shader draws, so without WebGL it is plain navy. Pauses off screen, one still frame under reduced motion. The loader's page snapshot drops `.gl` so the wordmark shows there.
- Hero type: mega wordmark at weight 700 with -0.06em tracking; the question headline at weight 500; big numerals at weight 300. Buttons are pills that grow 4% on hover and press to 97%. The navy section carries a 5% grain layer.

### Must work on mobile

- Layout must work at 360px width with 16px side gutters and no horizontal page scroll. Wide tables go inside a `.wrap` container that scrolls on its own.
- Tap targets at least 40px tall.

### Must be keyboard accessible

- Every control reachable and operable with Tab, Enter and Space. Visible focus ring on every interactive element (do not remove outlines).
- Every input has a `<label for>`. Use real `<button>`, `<a>`, `<details>` elements, not clickable divs.
- Loading and error states are announced in text, not just by a spinner or color change.

### Before saying a change is done

- Open the page in a browser (Playwright MCP if it is configured), run a query against the worker or a fixture, and take a screenshot at desktop and at 375px width.
- Check the quantified result, the fallback result, and an error response all render. Do not report done on syntax checks alone.
- If the worker is not reachable, say so explicitly in the final message instead of implying it was tested end to end.
